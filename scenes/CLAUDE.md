# scenes

Game scenes.

- `Run.tscn` (Node2D, main scene) holds `WellView`, an instance of `Ship.tscn`, the `Prediction` `Line2D`, `ReferenceMarker`, `FlightVector`, 3 `Body.tscn` instances (`Planet` index 0, `Moon1` index 1, `Moon2` index 2), the run-level `FlightCamera` and a `CanvasLayer` with a `ui/TuningPanel.tscn` instance (hidden on start, screen-fixed).
- `Ship.tscn` is a `CharacterBody2D` with `Ship.gd`, a `Polygon2D` triangle (nose toward local -Y) and a `CollisionShape2D` with a `CircleShape2D`. It has no camera: there is one camera, `FlightCamera`.
- Flight physics is the pure `ShipFlight.step(state, input, t, dt) -> ShipState` (`class_name`, static, no scene dependency, so trajectory prediction can reuse it). It returns a new state, never mutates its arguments, and is deterministic. `ShipParams` are read from `Tuning.ship` on each call, no cache. Any new flight feature goes into the state and `step`, not into the `Ship` node.
- Step order: rotation, control branch, heat, translation. The control branch is an elif chain, soft brake > drift sync > boost / thrust; held actions do not add up. Rotation is manual `turn` or, with `has_heading`, a critically damped PD toward `target_heading`; spin damping is always on; `rot` stays wrapped to [-PI, PI]. Thrust acts along the nose `Vector2.UP.rotated(rot)`. Translation is semi-implicit Euler in the rotating frame: gravity, `frame_accel`, thrust and brake terms, then position. A ship at rest at the carrier stays there. Accepted cost: explicit Coriolis in semi-implicit Euler drifts band-drift orbits at large Ω_f; D35-scale Ω_f is not affected (`docs/production/tech-debt.md` #7).
- Thrust, ramp and heat (D36): holding the engine (thrust or boost) grows `hold_time`; the thrust scale is `lerp(ramp_min_fraction, 1, hold_time / ramp_time)`, so a short tap is a weak but non-zero impulse. Every other branch resets `hold_time`. `heat` in [0, 1] grows on the engine (faster on boost) and cools on every non-engine branch, so brakes never heat; above `heat_threshold` thrust falls linearly to `min_thrust_fraction` at full heat (boost inherits). `boost` alone gives `thrust_accel·boost_accel_mult`. Fuel is per actually applied delta-v with a separate counter per mode (`fuel_engine`, `fuel_boost`, `fuel_soft_brake`, `fuel_sync`); fuel only accumulates, there is no tank limit.
- Soft brake (`ship_brake`) lives in `step`, so prediction stays equal to flight. Its acceleration is half of `brake_accel` against velocity plus half backwards from the nose; near rest only the nose half is applied. Thrust and boost are ignored while it is held, rotation still works, no heat.
- Drift sync (`ship_drift_sync`): the reference is the pure `ShipFlight.sync_reference(pos, t) -> {valid, index, is_carrier}`; candidates are all bodies and the carrier point, the nearest strictly within `sync_radius` wins (a body on a tie), recomputed each step and never stored. With a reference the ship is pulled to the reference velocity (zero for the carrier, `body_vel` for a body) at no more than `sync_accel`. Thrust and boost are ignored, no heat, rotation works, fuel is more expensive than the engine.
- Drift-sync fallback (no reference within `sync_radius`, `_band_drift_accel`): converge to the band drift of the current depth around `reference_body` (= `GravityField.dominant`). The math is done in the rotating frame: the orbit direction is taken from the inertial relative velocity (so a retrograde ship stays retrograde; near-radial velocity falls back to counter-clockwise) and the target is the circular velocity around the body expressed back in the rotating frame. It is clamped by `sync_accel`, independent of the nose, and billed like sync. Accepted costs: near a moon the planet pull also acts, so the target is not exactly circular; a reference switch jumps the target, smoothed only by the clamp.
- `ReferenceMarker` marks the sync reference: a ring at the reference body or carrier point, hidden when there is no reference. The ring has a constant screen size (world radius = `RING_PX * s`), brighter while `ship.input.drift_sync`. View-only: reads the ship, never writes flight state.
- `FlightCamera.gd` (`class_name`, Camera2D in `Run.tscn`) is the local-vertical camera (D35). Pure statics: `rotation_for(pos)` makes screen-down point at the planet center from any position; semantic zoom s ("s times more world per screen", 1x = 1280x800 units) is clamped to [1, 40], continuous up to 22 and then stops 28 / 34 / 40; `zoom_vector(s)` inverts it for `Camera2D.zoom`. The node follows the ship, rotates by `rotation_for` (`ignore_rotation = false` in `_ready`; Godot 4 defaults to true, which silently drops the rotation), eases s in s-space, and reads `camera_zoom_in` / `camera_zoom_out`. It scales only the ship's `Polygon2D` icon by s (constant screen size); `ship.scale` and the collision shape are never touched. No autozoom. View-only.
- `FlightVector.gd` is the velocity arrow from `ship.state.pos` along the current velocity only (no acceleration term), its shaft is |v| long in WORLD units (honest 1:1), head and stroke have constant screen size, hidden below 1 u/s. Always shown; the prediction line is separate. View-only.
- `WellView.gd` draws the well as honest arcs: planet surface, atmosphere edge and `r = const` orbits (the carrier orbit plus orbits of bodies with `parent == 0`), read from `Tuning.field` on every draw. Stroke widths are constant screen pixels (world = px * s). The carrier orbit keeps its own stronger style at any zoom; other orbits are highlighted when zoomed far out (s >= 22). Special boundaries (`atmosphere`, `tow`, `ceiling`) are solid circles with their own `boundary_style(kind)` (tow yellow, ceiling red, atmosphere keeps the blue stroke), distinct from every `orbit_style`. `annulus_points(r_in, r_out, a0, a1)` is the static tier-band polygon: outer arc a0→a1 then inner arc a1→a0, point count per arc from `_segments`. `tier_bands()` (static) returns the 4 bands bottom to top (`r_in`, `r_out`, placeholder `color`) on `WellGenerator.tiers()` boundaries; `_draw` fills them first (semi-transparent, over `band_span` = the widest visible span across the band, so a camera inside a band still sees its tint; `band_polygons` splits a full-circle band into two half-annuli because the slit annulus does not triangulate), under surface, orbits and boundaries. `special_rings()` (static) lists the atmosphere edge, tow and ceiling at generator radii, drawn with `boundary_style`. The carrier point is marked at `(carrier_orbit_radius, 0)`. Arcs are drawn for the visible part only, with a segment count that bounds the chord sagitta. Redraws every frame and on `preset_applied`. View-only.
- `ShipState` (pose, rotation, fuel counters, `hold_time`, `heat`) and `ShipInput` (`turn`, `has_heading`, `target_heading`, `thrust`, `boost`, `soft_brake`, `drift_sync`) are `RefCounted` with typed fields and a field-by-field `copy()`; prediction == flight depends on `copy()` being complete. Ramp and heat state live in `ShipState`, not on the node. `ShipInput.screen_heading(stick, pos)` converts a gamepad stick to a world heading relative to the camera (adds `FlightCamera.rotation_for(pos)`), so stick-up is screen-up.
- `Ship.gd` holds the authoritative `state`. `_ready` calls `respawn()`, also connected to `Tuning.preset_applied` (a preset load respawns at the carrier of the new field; slider edits do not). `respawn()` puts a fresh `ShipState` at rest at the carrier point `(carrier_orbit_radius, 0)` with the nose away from the planet (`rot = FlightCamera.rotation_for(pos)`). `_physics_process` builds a `ShipInput` from the actions, keeps it in `input`, steps with the fixed `GravityField.DT` and `GravityField.time()` (read after the tick increment, like `Body`), then `move_and_collide(state.pos - position)` and `rotation = state.rot`. Accepted cost: with no colliders `state.pos` is the node position; once something collides they diverge and need syncing.
- `ShipPrediction.run(state, input, tick, steps) -> PackedVector2Array` (`class_name`, static, pure) repeats `ShipFlight.step` with `t = GravityField.time_at(tick + i + 1)`, returning the position after each step. It starts from `ship.state` and is bit-identical to real flight with the same input. It takes any N.
- `Prediction` is a `Line2D` after `Ship` in `Run.tscn` (reads the already-stepped state), not a child of `Ship`. It is always shown. The line is computed from `ship.input` with `turn` zeroed (a held rotation would spin the replayed ship and degenerate the line to coasting); the heading target and state are kept. The width is constant screen size (`2 px / cam.zoom.x`, refreshed every frame). Recomputed every `maxi(predict_every, 1)` ticks and at once on `preset_applied` (after the ship respawn). There is no full-trajectory mode; the Otryv scene will call `ShipPrediction.run` with its own N. Accepted cost: the line passes through bodies (they have no radius); recompute cost is `docs/production/tech-debt.md` #6.
- Input actions live in `project.godot` `[input]`: `ship_rotate_left/right` (A / D), `ship_thrust` (W, right trigger), `ship_boost` (Space, joypad button 0), `ship_brake` (S, left trigger; the soft brake), `ship_drift_sync` (Shift, left stick click), `ship_heading_*` (left stick), `camera_zoom_in/out` (wheel, d-pad), `debug_tuning_panel` (F1, handled in the panel's `_unhandled_input`; flight input stays live while it is open). A stick beyond the deadzone sets `has_heading` with a screen-relative target; otherwise A / D give `turn`.
- `Body.tscn` is a view: Node2D with `Body.gd` (`@export var index`) and a placeholder square visual. Each physics tick it sets `position = GravityField.body_pos(index, GravityField.time())`; it is hidden while `index >= Tuning.field.bodies.size()` (the default field has only the planet). The visual keeps a constant screen size (scaled by the camera's semantic zoom; moons use `MOON_SCALE` 0.6 and a bluish tint). Params live in `Tuning.field`, not on the node.
- `Carrier.tscn`, `Field.tscn` are empty `Node2D` roots.
