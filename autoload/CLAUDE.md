# autoload

Global singletons registered in `project.godot`.

- `GravityField` is the pure field math: `accel`, `potential`, `potential_eff`, `body_pos`, `body_vel`, `frame_accel`, `frame_omega`, `circular_speed`, `dominant` depend only on their arguments and `Tuning.field` (read on each call, no cache, no node state), so any `t` can be queried. Time is `tick` (int, +1 per `_physics_process`); `DT = 1/60` is the one fixed step, `time_at(n) = n / 60.0` (any tick, used by prediction) and `time() = time_at(tick)`.
- All field mechanics live in the frame rotating with the carrier (D35): body positions and velocities are relative to that frame, `ShipFlight.step` adds the frame terms (`frame_accel`), and the honest gravity g(r) is unchanged. `frame_omega` still makes `g_eff(r_c) = 0` at the carrier orbit; within the frame the carrier itself patrols its orbit at the linear `Tuning.planet.carrier_patrol_speed` (`ShipFlight.carrier_pos/carrier_vel`, see `scenes/CLAUDE.md`).
- Per body g(r) = k·M / (r^p + ε), p per body; ε is only in g; Φ is the antiderivative at ε = 0, so −∇Φ ≈ accel only away from body cores. Moon pull (`influence_radius` R > 0) fades by smoothstep to 0 over [R, R·(1+`fade_width`)]; Φ in the fade zone is a numeric integral.
- `body_pos(i, t)` is a circular orbit at the angular speed relative to the frame (`angular_speed − frame_omega()`); `body_vel` is its analytic derivative (parent's velocity added), zero for the planet. `parent = -1` is the origin.
- `accel_of(i, pos, t)` is the fade-weighted pull of body i; `accel` is the sum. `dominant` is the body with the largest `|accel_of|`. `circular_speed(i, pos, t)` is `sqrt(r_i·|accel_of|)` with only body i's pull (0 at its center); the drift-sync fallback uses it.
- `frame_omega()` is derived from the planet pull (`bodies[0]`, fade included, moons ignored) at `carrier_orbit_radius`, recomputed on each call (no cache) so g_eff(r_c) = 0 for any p and any slider. The planet pull is computed from the g(r) formula directly, not through `accel_of` (which calls `body_pos`, which calls `frame_omega`: infinite recursion); a test pins the equality. The carrier is not a body and not a gravity source.
- `planet_potential_eff(r)` is the radial Φ_eff of the planet alone: planet `_phi_body` minus ½·`frame_omega()`²·r², no `t`, no moons, reads `Tuning.field` per call. Strictly increasing on [`atmosphere_edge`, `carrier_orbit_radius`]; the generator root-finds on it.
- `frame_accel(pos, vel)` is centrifugal plus Coriolis; the only place of this math. `potential_eff` is `potential` minus the centrifugal term and is the single effective potential (tiers, return margin, economy); `potential` stays pure gravity.
- `Tuning.field` is a `FieldParams` Resource (`k`, `eps`, `fade_width`, `planet_surface_radius`, `atmosphere_edge`, `carrier_orbit_radius`, `bodies: Array[BodyParams]`); `BodyParams` has `mass`, `p`, `influence_radius` (0 = unlimited), `radius` (0 = no physical body; > 0 is a solid disc, used by moons for contact and the visual), `parent`, `orbit_radius`, `angular_speed`, `phase`. The code default (script defaults and `Tuning._default_field()`) is the D35 scale: surface 100 000 < atmosphere edge 101 500 < carrier orbit 121 500, a single planet. `Tuning._ready` loads nothing: a fresh start runs on the code defaults and presets are applied only from the panel. A multi-body preset applied on the single-body default is fine: `Tuning.apply` accepts any body count.
- `Tuning.ship.hit_radius` (15) is the ship circle for small-body contact; the other ship params are unchanged.
- `Tuning.planet` is a `PlanetParams` Resource (`class_name`, `@export`), built in code by `Tuning._default_planet()`, the same for every preset (not in `TuningPreset`, untouched by `apply` / `save_preset` / `load_preset`); read per call, never cached. Holds `tier_shares` (top to bottom `[0.25, 0.40, 0.25, 0.10]`), `ceiling_offset` (5000, ceiling = carrier orbit + offset), `carrier_patrol_speed` (default 0 = the carrier rests; 40 u/s was the playtest value; the carrier's LINEAR speed along its orbit IN the rotating frame, must stay ship-reachable — an angular period there would be ~2000 u/s at R_c ≈ 110000, faster than any ship; patrol postponed to week 4 (docking): co-moving rest is not stable and the return estimate assumes a resting carrier), moon generation data (`moon_count_min/max` 2..3, `moon_large_radius_min/max` 1000..2000 on high orbits, `moon_small_radius_min/max` 300..700 on low orbits; mass `moon_mass_k` 0.001032 and `moon_mass_exp` 1.79, `influence_radius = moon_influence_k` (1.2) `· radius`, `moon_margin` 100 spacing for `WellGenerator.check`, `max_tries` 8 and `fallback_seed` 2 for `picture`; moon contact `moon_bounce` 0.5 restitution and `moon_impact_damage` 0.05 hull per unit of impact speed; see `gen/CLAUDE.md`), the ring (`ring_tier` 2, an index into `boundaries` bottom-up; `ring_width` 1500 and `ring_density` 0.5 of `RingView.MAX_PARTICLES`, invented numbers, `ring_dust_density` 0.5 of `RingView.DUST_MAX` (the non-interactive dust specks, `scenes/CLAUDE.md`; playtest hypothesis), `ring_drag_tau` 15.0 s of ring-drag relaxation (`scenes/CLAUDE.md`), playtest hypothesis), asteroid bands and fields (`band_width` 1500, `chunk_arc` 4000, `ring_boulders_per_chunk` 1.0 (≈ one `ore_middle` boulder per chunk in the ring band, the ring's mining mechanic, `gen/CLAUDE.md`; playtest hypothesis), `chunk_gen_radius` 20000, `asteroids_per_band` 200 (expected asteroids in one band around the whole planet, set by playtest; on the default field the per-chunk field chance reaches 1 near 720, so higher values add nothing), `drop_start` 6 bands from the carrier, `drop_ratio` 0.6, `above_factor` 0.1, `field_radius` 600, `ast_radius_min/max` 40..120; see `gen/CLAUDE.md`), asteroid contact (`asteroid_bounce` 0.5, `asteroid_impact_damage` 0.05; all placeholders for O47), piece contact (hypotheses; see `scenes/CLAUDE.md`): `piece_swallow_radius` 25, `piece_despawn_radius` 3000, `piece_bounce` 0.5, `v_safe` 12 and `impact_k` 0.05 of the quadratic `impact_damage`. Beam split and pieces (M5, D40, D41, hypotheses; see `scenes/CLAUDE.md`): `split_count` 3 pieces per break, `split_area_divisor` 1.5 (the pieces of a break together cover the parent area / divisor), `collect_radius` 20 (a body with `radius` at or below it is collectible and never hit by the beam), `break_per_sqrt_radius` 0.5 (beam charge needed to break = k · sqrt(R_eq), R_eq the hull's area radius; an r20 hull takes about 1.55–2.11 s at `beam_damage` 1), `piece_lifetime` 100 s (base lifetime; a piece lives `piece_lifetime · max(1, radius0 / collect_radius)`), `piece_min_radius` 5 (a piece's area shrinks linearly to the area of this radius over its life), `piece_spread` 0.7 (start offset in parent area radii), `piece_scatter` 5/3 outward speed of a piece. There are no scheduled small bodies and no `small_*` params (pinned absent by a negative test). `rest_speed` 0.3 (resting contact: below it the relative normal velocity is cancelled, no bounce, no damage; shared by moon and asteroid contact; slider 0..2). Atmosphere: `atmosphere_drag` 0.5 1/s at ρ = 1, `atmosphere_damage` 5.0 hull/s at ρ = 1, `density_shape` 2.0 exponent; playtest hypotheses. Radii stay in `FieldParams`.
- `Tuning.view` is a `ViewParams` Resource (`class_name`, `@export`), built in code, the same for every preset (not in `TuningPreset`, untouched by `apply` / `save_preset` / `load_preset`); read per frame by the view layers, never cached. Holds the gravity halo look knobs `halo_alpha` (0.25), `ring_count` (int, 4 rings over the zone), `ring_period` (2.0 s), `ring_px` (1.5, ring width in screen px), `ring_alpha` (0.5); ship fade `ship_fade_threshold_px` (12.0, screen px of full look span below which the ship fades out) and `ship_fade_width_px` (6.0, cross-fade width, so 9..15 px at the defaults); starfield knobs `star_cell0` (418.0, base world cell size, the 3 layers sit at `star_cell0`·8^i), `star_per_cell` (int, 1 star per cell), `star_fade` (1.0, layer cross-fade width in log2(s)) and `star_px` (1.5, star size in screen px); playtest guesses.
- `Tuning.ship` is a `ShipParams` Resource (`class_name`, `@export` fields), default built in code. Groups: flight (`thrust_accel`, `boost_accel_mult`, `turn_accel`, `spin_damping`, `heading_gain`, `climb_coefficient`, `boost_fuel_mult`, spawn `spawn_descend_speed` 5.0 u/s — the ship's spawn velocity toward the planet in `Ship.respawn()`, not co-moving with the carrier; playtest hypothesis); D36 controls (`brake_accel`, `brake_fuel_mult`, thrust ramp `ramp_time` and `ramp_min_fraction`, heat `heat_growth_engine` / `heat_growth_boost` / `heat_threshold` / `heat_cooldown` (0.18) / `min_thrust_fraction`, drift sync `sync_accel` / `sync_fuel_mult` / `sync_radius`); beam and collector (D40: `beam_range`, `beam_damage` 1.0 charge per second, `collect_angle` 60 degrees (full sector angle), `collect_accel` 200 pull acceleration; the old per-second extraction rate is gone); hull (`hull_max` 100.0); hold and mass (`hull_mass` 4.0, `hold_capacity` 10 cells, `ref_mass` 10.0 = start mass 4 + 2 × 3, `loadout_fuel_cells` 2, `tank_capacity` 4 (D38); return estimate `return_margin` 1.2 (slider 1.0..3.0, multiplies `Fuel.climb_energy`); defaults keep old `.tres` loading unchanged; `ref_mass` is the mass at which thrust, brake and sync accelerations are as tuned, see `scenes/CLAUDE.md`); prediction (`predict_short_steps`, `predict_every`); jettison (M7, D42, hypotheses: `jettison_tap_time` 0.7, `jettison_hold_time` 2.0, `jettison_interval` 0.7, `jettison_push` 5, `jettison_pickup_delay` 1.5; see `scenes/CLAUDE.md`). `climb_coefficient` 0.05 (prototype calibration, D38; economy.md has 0.2) is the energy of a clean climb from the middle of the middle tier per unit of mass (`Fuel.per_dv`, see `scenes/CLAUDE.md`). D36 values are playtest hypotheses. There is no `predict_full_steps` (`ShipPrediction.run` takes any N) and no `spawn_radius` (the ship spawns at the carrier). Every parameter except preset-level constants and the `Tuning.view` ship fade knobs (`ship_fade_threshold_px` / `ship_fade_width_px`) and starfield look knobs (`star_cell0` / `star_per_cell` / `star_fade` / `star_px`), all code defaults without sliders, is a `TuningPanel` slider (`ui/CLAUDE.md`).
- `ShipParams` M9 fields: `refiner: bool = false` (amplifier: refines transferred ice into 1/3 fuel instead of raw ice cells), `transfer_hold_time` 1.0 and `transfer_interval` 0.7 seconds (playtest hypotheses).
- `Tuning.resources: Dictionary` maps StringName to `CellType` (`class_name`, Resource: `mass`, `volume`, `energy`), built in code by `Tuning._default_resources()`, not in `TuningPreset` (untouched by `apply` / `save_preset` / `load_preset`); read per call. Types (mass / volume / energy): `ice` 1/1/1, `ore_base` 1/1/0, `ore_middle` 2/1/0, `ore_rare` 3/1/0, `ore_unique` 3/1/0, `fuel` 3/1/3. Volume is 1 for every type (one cell = one slot). The tank (D38, the only fuel mode): a limited `tank_capacity` store outside the hold that holds fuel and raw ice moved in by the transfer. Burning (`Hold.drain`, see `scenes/CLAUDE.md`) takes the tank's ice first, then its fuel; hold ice and ore are cargo and never burn. Ore has energy 0.
- `TuningPreset` (`class_name`, Resource: `name`, `field`, `ship`) is one `.tres` per preset in `res://presets/` (`p1`..`p4`, `name` «P1 Ньютон», «P2 Плоский 2D», «P3 Компромисс», «P4 Смешанный»), all rescaled to D35: `k`, `eps`, `fade_width` and the three radii are explicit in each file. Planet p: P1 2, P2 1, P3 1.5, P4 2; the planet is static. Presets are planet-only: `bodies` holds just the planet (mass per the p recipe); moons are not stored in `.tres` and are generated at runtime (`Tuning.regenerate`). No force normalization in code.
- Fair comparison (D29/D35) is a property of the planet curve: planet mass is chosen per p so the Φ_eff drop between the carrier orbit and the atmosphere edge is equal across presets (the p = 2 recipe sets the target). Consequently Ω_f and the band drift differ by preset; this is intended and visible in A/B. A test pins the equal drop on planet-only fields.
- The ship sub-resource of each `.tres` carries every `ShipParams` field equal to the code defaults (except P4: `thrust_accel` 30.5), so loading a preset sets a known ship state.
- `Tuning.apply(preset, emit := true)` replaces `field` and `ship` with deep copies (slider edits never touch the cached resource; no game code caches `Tuning.field` / `Tuning.ship`) and emits `preset_applied` unless `emit` is false (the panel's Load passes false and lets `regenerate` emit once). `Tuning.load_preset(path) -> TuningPreset` loads uncached; `Tuning.save_preset(path, name) -> Error` saves deep copies of the current state with only `bodies[0]` (the planet), so generated moons never reach a preset.
- `Tuning.lock` (`Mutex`) guards structural changes of `Tuning` against the `Prediction` worker task, which holds it for the whole `ShipPrediction.run`: a replaced `field` / `field.bodies` mid-run makes the run fail (out-of-bounds body index), not merely drift. `Tuning.apply` and `Tuning.regenerate` take it around the replacement, so the main thread waits at most one run, and only on a preset load, seed change or generation slider (a drag regenerates per value change; accepted). Scalar slider writes take no lock (accepted risk: the next run corrects the line). Code that swaps `Tuning.field` / `planet` directly while a `Prediction` line is alive takes `Tuning.lock` or waits for its task. Lock order is always `Tuning.lock` → `WellGenerator._lock`. A `Tuning` snapshot passed to the worker is not used, because it would have to be threaded through `GravityField` / `ShipFlight` / `AsteroidField` / `SmallObjects`.
- `Telemetry` (`extends Node`) holds `crashes: int` (starts 0), incremented by `Ship` on a crash respawn; a preset change does not reset it. `transfers` (int, M9) counts actual transfers: `Ship` increments it after the step when `ShipFlight.step` reported that `Hold.transfer` moved ice (no pre-step check). Int counters `jettisons`, `jettison_selects`, `jettison_cancelled` (start 0) are incremented by `Ship` (`scenes/CLAUDE.md`, LongPress). With `--flight-log` the `FLOG respawn` line prints `crashes`, `jettisons`, `jettison_selects`, `jettison_cancelled` and `transfers`. `seed` and `flight` (int, both start 1) are the picture currently shown: `seed` is the seed used, which may differ from the requested one when `picture` retried (the next seed is `seed + 1`).
- `Tuning.regenerate(seed, flight)` asks `WellGenerator.picture`, replaces `field.bodies` with `[bodies[0]]` (the planet) plus the generated moons (so repeated calls never accumulate), writes the used seed and flight to `Telemetry.seed` / `Telemetry.flight` and emits `preset_applied` once (so `Ship` respawns, also when a generation knob triggers it). `Tuning.apply` alone leaves the current moons out (a preset has none); the panel and `Run.gd` follow it with `regenerate`.
- `Tuning.picture` is the whole generated picture `{seed, flight, moons, ring}` from the last `regenerate` (the ring and the moon-blocked bands are read from it per call, never cached by consumers, like `Tuning.field`). Before any regenerate it is `{seed: 1, flight: 1, moons: [], ring: {}}` (planet only, no ring). `regenerate` stores the full `picture()` dict and still emits `preset_applied` once.
